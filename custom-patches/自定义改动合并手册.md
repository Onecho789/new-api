## 〇、remote 约定（重要）

自 2026-07-31 起，本仓库有两个 remote，**别搞反**：

| remote | 指向 | 用途 |
|---|---|---|
| `origin` | `github.com/Onecho789/new-api`（你自己的 fork） | **推送**你的代码 |
| `upstream` | `github.com/QuantumNous/new-api`（官方上游） | **拉取**上游更新 |

新机器 clone 后需补配：

```bash
git remote add upstream https://github.com/QuantumNous/new-api.git
```

自定义改动**已提交进 git**（不再是工作区未提交状态），所以本地相对上游是 ahead 的，
合并上游要用 `git rebase upstream/main` 而不是 `--ff-only`。

## 一、快速合并（照抄即可）

```bash
cd "D:/2api-codes/newapi/new-api"

# ── 1. 备份 ───────────────────────────────────────────────
TS=$(date +%Y%m%d-%H%M%S); BK="custom-patches/backup-$TS"; mkdir -p "$BK"
git rev-parse HEAD > "$BK/base-commit.txt"
git format-patch upstream/main --stdout > "$BK/local-changes.patch"   # 已提交状态用 format-patch
cp common/model_mask.go "$BK/model_mask.go.bak"

# ── 2. 合并上游（rebase，把你的定制提交叠到最新上游之上）──
git fetch upstream --prune
git log --oneline HEAD..upstream/main         # 先看上游改了什么
git rebase upstream/main                      # 冲突则见「五、冲突处理」

# ── 3. 校验标记（预期 1 2 2 1 1 4 1 2）────────────────────
grep -c CUSTOM \
  service/log_info_generate.go service/task_billing.go controller/relay.go \
  common/model_mask.go service/http.go relay/helper/common.go \
  web/src/features/usage-logs/lib/format.ts \
  web/src/features/usage-logs/components/dialogs/details-dialog.tsx

# ── 4. 验证 ───────────────────────────────────────────────
go build ./common/... ./controller/... ./service/... ./relay/... ./model/... ./middleware/... ./setting/... ./oauth/... ./pkg/...
go vet   ./common/... ./controller/... ./service/... ./relay/...
(cd relaykit && GOWORK=off go build ./... && GOWORK=off go test ./...)
go test ./common/... ./relay/helper/... ./controller/...
(cd web && bun run typecheck)

# ── 5. 刷新备份并推送到自己的 fork ────────────────────────
git rev-parse HEAD > "$BK/merged-to-commit.txt"
git format-patch upstream/main --stdout > "$BK/local-changes.patch"
git add -A && git commit --amend --no-edit    # 把刷新后的备份并入定制提交（可选）
git push --force origin main                  # rebase 后历史变了，必须 force
```

**注意事项**

- `go build ./...`（带 main）会报 `pattern web/dist: no matching files found`。这是**正常的**，因为 `web/dist` 只在 Docker 构建时生成。所以第 4 步刻意跳过了 main 包。
- `relaykit/` 是**独立 Go module**，AGENTS.md 强制要求用 `cd relaykit && GOWORK=off go build ./...` 单独验证；从根目录跑 `go test ./relaykit/...` 会 `setup failed`，属预期。
- 前端检查前需要依赖：`cd web && bun install --frozen-lockfile`（`node_modules` 不在版本控制内）。若 `bun: command not found`，先 `npm i -g bun`。
- 不要跑 `bun run lint` / `format:check` 来判断成败——上游自己就有一堆报错。只需确认报错**不涉及**你改的那 2 个前端文件（见「七」）。

**4b. 新增函数**（文件末尾附近，紧跟在某个 `return true }` 之后）：

```go
// CUSTOM: customMaskUpstreamModelInText 将报错文本中出现的"实际上游模型名"替换为用户请求的模型名。
// 场景：请求模型经渠道 model_mapping 映射为上游模型后，若上游报错并在错误消息里带上上游模型名，
// 该真实模型名会通过错误日志的 content 字段泄露。这里根据渠道映射表反查出 requestModel 对应的
// 上游模型名（含链式映射），逐一替换回 requestModel，确保报错日志同样只暴露请求模型。
// 若无映射或解析失败，则原样返回，不影响正常报错内容。
func customMaskUpstreamModelInText(c *gin.Context, requestModel string, text string) string {
	if text == "" || requestModel == "" {
		return text
	}
	modelMapping := common.GetContextKeyString(c, constant.ContextKeyChannelModelMapping)
	if modelMapping == "" || modelMapping == "{}" {
		return text
	}
	modelMap := make(map[string]string)
	if err := common.UnmarshalJsonStr(modelMapping, &modelMap); err != nil {
		return text
	}
	// 沿映射链收集 requestModel 对应的所有上游模型名（带循环保护）。
	current := requestModel
	visited := map[string]bool{current: true}
	for {
		mapped, ok := modelMap[current]
		if !ok || mapped == "" || visited[mapped] {
			break
		}
		visited[mapped] = true
		current = mapped
	}
	for upstreamModel := range visited {
		if upstreamModel != "" && upstreamModel != requestModel {
			text = strings.ReplaceAll(text, upstreamModel, requestModel)
		}
	}
	return text
}
```

**恢复**：调用点还原为单行直接传参，删除该函数。

⚠️ **排障提醒**：这会让**你自己**在管理后台看到的报错日志里的模型名也是伪装后的请求模型名。排查上游问题时请留意这一点。

> ### ⚠️ #5 #6 必读：为什么用具名常量而不是硬编码 `false`
>
> 早期版本写的是 `const isMapped = false` 和 `{false && ...}`。这两种写法**过不了检查**：
>
> - `false &&` 短路会让 TypeScript 丢失 `other` 的 null 收窄 → `bun run typecheck` 报两处 `TS18047: 'other' is possibly 'null'`
> - `{false && ...}` 还会触发 ESLint `no-constant-binary-expression`
>
> 解决办法就是现在这个写法：具名常量 + **显式标注 `: boolean`**（标注是关键，否则 TS 把类型收窄成字面量 `false`，问题依旧），并把上游原判断表达式保留在与运算右侧。
>
> 重做这两处时，**不要**退回硬编码 `false`。

#### #7 `common/model_mask.go`（新增文件，102 行）

放在 `common` 包（`service` 和 `relay/helper` 都能 import，无循环依赖）。

导出一个函数：

```go
func MaskUpstreamModelInData(c *gin.Context, data []byte) []byte
```

内部逻辑：从 context 读 `original_model`（请求模型）和 `model_mapping`（映射表），沿映射链收集所有真实上游模型名，对响应数据做**加引号精确替换** `"上游名"` → `"请求名"`。

三个关键设计点：

- **加引号替换**：`"claude-sonnet-4-6"` → `"claude-sonnet"`。加引号避免子串误伤（`gpt-4` 不会误伤 `gpt-4o`），且对 OpenAI / Claude / Gemini / SSE 各种 JSON 格式通用，无需按渠道分别解析。
- **快速路径**：无 `model_mapping` 或映射后与请求模型一致时，零开销原样返回。
- **context 缓存**：首次算出的替换对缓存进 context（key `custom_model_mask_pairs`），后续流式 chunk 不重复解析 JSON。

**恢复**：删除此文件 + 移除 #8 #9 的 5 处调用。

**完整源码**：见备份 `custom-patches/backup-*/model_mask.go.bak`（或工作区当前文件）。

## 四、设计原理

### 为什么响应体脱敏选「统一出口拦截」

泄露点分散在几十个渠道适配器的流式 + 非流式路径中，分三类：

- **类型A**：显式 `.Model = info.UpstreamModelName`（cloudflare / coze / cohere / aws / gemini / ollama…）
- **类型B**：透传上游 `xxxResponse.Model`（convert.go / relay-claude.go / xai / ollama…）
- **类型C**：`IOCopyBytesGracefully` / `StringData` / `ClaudeChunkData` 直接透传上游原始 body/chunk（OpenAI/Claude/Gemini 默认路径，**最普遍**）

但无论哪一类、哪个渠道，响应最终都汇聚到极少数几个**统一发送出口**。在出口做一次字节替换，就能覆盖全部泄露点：

- **完整**：一处堵漏覆盖所有渠道/格式，包括未来新增的适配器
- **抗合并冲突**：只改 5 个底层发送函数，上游几乎不碰；逐点改要动 ~40 处，几乎每次合并都冲突
- **低风险**：不触碰各适配器的业务逻辑

### 为什么 #4 和 #7 是两个独立函数（没合并去重）

`customMaskUpstreamModelInText`（日志）和 `MaskUpstreamModelInData`（响应体）映射链逻辑相同，但**替换语义不同**：

- 日志脱敏做**无引号**全文替换 —— 错误消息是自由文本，模型名不带引号
- 响应体脱敏做**加引号**精确替换 —— JSON 字段值，加引号才能避免子串误伤

合并成一个函数反而要引入模式参数，保持分离更直接。

### 副作用与性能

- **副作用**：若助手回复正文里恰好出现被引号包裹的上游模型名，也会被替换成请求模型名。对「隐藏真实模型」这个目标而言可接受，且与报错日志脱敏策略一致。
- **性能**：仅当渠道配了 `model_mapping` 才替换；无映射时快速返回。有映射时每 chunk 一次小字符串替换 + context 缓存，开销可忽略。

## 五、冲突处理

`git stash pop` 冲突时，按「保行为、不保行号」的原则处理：

| 改动 | 处理原则 |
|---|---|
| **#1 #2 #3** | 上游改了日志写入逻辑时，只要保证「不写入 `upstream_model_name`」这个行为。上游新加的其他 `other[...]` 字段照常保留。 |
| **#4** | 调用点位置随上游变动无妨，只要确保写入错误日志前经过 `customMaskUpstreamModelInText`。函数本身可放文件任意位置。 |
| **#5 #6** | 上游若重构了 `formatModelName` 或详情弹窗结构，重新找到位置，把开关常量接到判断链**最前面**。**不要**退回硬编码 `false` / `{false && ...}`（见 #5 #6 的必读框）。 |
| **#7** | 独立新增文件，一般不冲突。 |
| **#8 #9** | 上游若重构了这 5 个出口函数，只要确保发送数据前调用了 `common.MaskUpstreamModelInData(c, data)`。 |
| **#10** | 上游自己加了 `gpt-image-2` 则丢弃本地这处即可。 |

### 上游新增响应出口时（重要）

如果上游新增了响应发送函数（新的 SSE 出口、新的透传路径），**必须在新出口补上 `MaskUpstreamModelInData` 调用**，否则会漏。检查办法：

```bash
# 合并后看这两个文件是否新增了发送函数
git diff <合并前commit> <合并后commit> -- service/http.go relay/helper/common.go
# 排查是否有新的 CustomEvent 渲染点
grep -rn "common.CustomEvent{" relay/helper/ service/
```

### 用 patch 重放（stash pop 严重冲突时）

```bash
git checkout -- .                    # 放弃冲突的半成品（确认已有备份！）
git apply --3way custom-patches/backup-<时间戳>/local-changes.patch
cp custom-patches/backup-<时间戳>/model_mask.go.bak common/model_mask.go
```

patch 也 apply 不上，就按本文第三节 10 个改动点手工重做。
